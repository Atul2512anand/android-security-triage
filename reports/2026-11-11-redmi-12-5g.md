# Scan summary: Xiaomi Redmi 12 5G

**Scan date:** 11 November 2026  
**Device:** Xiaomi Redmi 12 5G, Android 15 / HyperOS  
**Method:** consented, non-root ADB triage: `adb bugreport`, MVT known-indicator
scan, APK pull, APKiD and androguard static inspection  
**Result:** 0 HIGH, 0 CRITICAL, 1 LOW, 14 MEDIUM MVT alerts

> This is a **redacted public summary**. The full case folder (bugreport, APKs,
> account dump, raw logs) was not published. Serial number, network addresses,
> account identifiers, per-service account counts, the personal app inventory
> and exact usage timestamps have been removed. The device model is retained
> because it is useful context and is not unique.

## Verdict

The phone is healthy at the system level. Verified boot is green, the
bootloader is locked, SELinux is enforcing, storage is encrypted, there is no
root binary, no device administrator and no enabled third-party accessibility
service. MVT found **no HIGH or CRITICAL** spyware indicators.

One real problem was found: a fake **PhonePe** app (`com.phonepe.spoof`) that
was sideloaded from a third-party APK site in January 2025. It has **no
INTERNET permission**, so it cannot exfiltrate data, but it can display a
convincing fake payment-success screen. It should be uninstalled.

A second unusual app is a Wi-Fi FPV drone controller (`FYD-FPV`). It matches a
legitimate consumer drone app and is not spyware.

### What it is

The manifest declares 12 activities that imitate a complete payment flow:
main, home, pay, paid, balance, add balance, PIN, scanner and check screens.
The APK also contains a large animated payment-success "tick". The package name
itself contains the word "spoof".

This is an impersonation app, not a banking trojan:

- It **cannot** open a network connection, so it cannot upload anything.
- It **can** show a fake "payment successful" screen.
- It **can** write images to shared storage.
- While open, it can read the clipboard (targetSdk 28 behaviour).

A fake success screen can be used to deceive a shop, delivery agent or friend
into thinking money was sent. It also occupies the "PhonePe" name on the
launcher, which can trick the owner into entering a real UPI PIN into a fake
screen.

### How it arrived

The recent-tasks dump recorded a Chrome tab for
`web:https://phonepeapk.com`, immediately followed by
`com.phonepe.spoof/HomeActivity`. This is a task/recent-app record, **not** a
copy of Chrome's History database.

On the same morning, Chrome and the Xiaomi file manager were allowed to install
packages shortly before the app was installed. This was a manual sideload from
a third-party APK website, not an app-store install. The real PhonePe app
(`com.phonepe.app`) is **not** currently installed.

### Action

1. Settings → Apps → Manage apps → PhonePe → Uninstall. Confirm the package is
   `com.phonepe.spoof`, not `com.phonepe.app`.
2. Install the real PhonePe only from Google Play.
3. If the fake app was used to show a payment to someone, treat that payment as
   not made and check the bank/UPI statement.
4. Change the UPI PIN from the real app afterwards.
5. Do not revisit `phonepeapk.com`. The official domain is `phonepe.com`.

suspicious background service, no SMS/contact access, no accessibility abuse.
Two privacy notes: Umeng sends app/device usage data to Alibaba, and the app has
INTERNET permission even though flight uses the local drone Wi-Fi. If the drone
is no longer used, uninstall it.

## 3. MVT alerts explained

MVT reported **0 HIGH, 0 CRITICAL, 1 LOW, 14 MEDIUM**.

**LOW - accessibility.** MVT counted 10 accessibility services installed on the
system, but `accessibility_enabled=0`; those are built-in Xiaomi/Google
services that are switched off. The dangerous pattern would be an *enabled*
third-party service.

**MEDIUM - app-ops (10 alerts).** The same few entries repeat across snapshots:

- `com.android.shell` location access: this is ADB, i.e. the scan itself.
- Chrome and the Xiaomi file manager were allowed to install APKs around the
  fake PhonePe install in January 2025. This is the install path.
- A messaging app was allowed to install an APK in March 2025. The owner first
  rejected and then allowed it 22 seconds later, a normal "install an APK a
  contact sent me" flow. No matching app remains from that date.

**MEDIUM - battery daily (4 alerts).** These are uninstall/reinstall events for
ordinary consumer apps (rail, payments, food delivery). Android records such
cycles routinely; nothing to do.

MVT compares against public spyware indicator lists. A clean result does not
mathematically prove the phone is clean, but combined with the integrity checks
below it is a good result.

## 5. Profiles and accounts

Two Android profiles exist: the owner profile and Xiaomi Second Space (XSpace),
which is empty: 0 accounts, no suspicious packages, no device administrator.

The owner profile has **24 account entries** across Google, Instagram, X,
Reddit, WhatsApp, Telegram, Microsoft 365 and Xiaomi services. Only names,
types and add/remove history were collected, and Android itself masked the
names in its `dumpsys` output (for example `a***@gmail.com`). No passwords,
OAuth tokens or recovery codes were collected.

The account history shows a social app repeatedly removing and re-adding its own
account entry while multiple accounts were logged in. That is normal account-sync
churn, not an intrusion. No account was added or removed by an unknown app.

## 6. Data scope: what was and was not collected

Collected:

- system snapshot (`adb bugreport`): build properties, mounts, SELinux,
  verified-boot state, `dumpsys activity` recents, package metadata,
  app-ops, accessibility, device policy, connectivity, battery, settings,
  processes, bounded logcat, ANR traces, tombstones, vendor stability logs;
- 8 pulled APKs with SHA-256 hashes, including the fake PhonePe APK;
- MVT parse of the bugreport: alerts, timeline and parsed `dumpsys` snapshots.

**Not collected:** Chrome `History`/cookies/logins, WhatsApp `msgstore.db` or
media, SMS/MMS, call log, contacts, photos/DCIM/EXIF, Gmail/social message
content, Keystore, saved passwords, clipboard or any `/data/data/<app>`
sandbox file. Non-root ADB cannot read those paths, and `adb backup` is not a
reliable substitute on modern Android.

`dbinfo.json` in the MVT output lists database paths and SQL statements seen in
runtime logs. It does not contain the rows of those databases.

## 7. Recommendations

1. Uninstall `com.phonepe.spoof`.
2. Install the real PhonePe from Google Play if needed.
3. Confirm the FYD drone app is expected; uninstall it if the drone is gone.
4. Review the accounts on the phone with the owner.
5. Keep or remove Second Space depending on whether it is used.
6. Turn off Developer options and USB debugging when finished.
7. Re-run the full scan after the uninstall to keep a clean record.
8. Close ADB TCP port 5555 (reconnect USB and run `DISABLE-ADB-TCPIP.bat`, or
   restart the phone).

## Reproducing this scan

The toolkit is in this repository. Start with `START-HERE.bat`, connect the
phone with consent, and choose **FULL scan**. A bugreport can take 5-15 minutes
over a remote connection.

Case data stays local in `cases/` and is excluded from Git. The included
`ADB-TCPIP-HELPER.zip` provides ADB plus enable/disable scripts for the USB
fallback when Wireless debugging and Tailscale conflict.
